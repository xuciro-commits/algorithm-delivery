## 三、四个裁决点（逐条回答）

1. **要不要为性能解除零第三方依赖（OPT-02）？→ 不要。**
   SRS §12 明文非目标；且本轮七项优化**一行外部 crate 都没用**就拿到
   880×（X01 生成）、33×（解析）、25×（核验）。
   结论：**维持零依赖**。

2. **要不要引入多线程 / 并行（rayon、`std::thread`）？→ 不要作为默认路径。**
   ① WASM 端是单线程，"原生快、浏览器慢"会让同一份契约出现两条性能口径；
   ② 并行会破坏「同种子逐位可复现」（我们全部回归比对都靠 assignment 哈希）；
   ③ 现在的瓶颈是**算法复杂度**而不是并行度——复杂度修完，2 vCPU 沙箱上已经是秒级。
   结论：**单线程 + 修复杂度**。

3. **要不要按档位降级 / 阻断重型场景（OPT-05/06）？→ 降级可以（能力分档已存在），阻断要你签字。**
   建议折中：跑之前按档位如实给出「预计耗时 / 内存」，超阈值二次确认，**不静默拒绝执行**——
   交付物要求「诚实报告」，而不是把规模藏起来。

4. **要不要调整默认参数或验收口径（stress 档进默认验收 / 调小默认迭代数）？→ 不要动。**
   默认 86 场景验收本来就把 stress 档排除在默认路径外，只接受 `--scale` / `--ids` 手动触发；
   30 s 预算的语义是「如实给出已解规模 + 界」。性能问题在算法侧解决比改口径更诚实。
   结论：**参数与验收口径不动**。

## 四、为什么「看起来最该改」的那两处反而不改

- **`Json::obj.get`**：对象字段线性查找的代价是「字段数」，不是「元素数」。
  实测大文档解析层的时间几乎全在 `contract.rs` 的引用检查（现已 O(1)）。
  把 JSON 换成哈希表能省的是常数级，换来的是输出规范与确定性风险——不划算。
- **`generate` 的整树序列化**：X01 文档 344.9 MB，构建期峰值 ≈3.7 GB。
  这是"结构决定"（问题文档自包含：顶层一份拓扑 + 问题内一份拓扑），
  不是 bug；要压得动整棵 JSON 树的表示，属于单独排期的事，不应混在"修 O(n²)"里做。

## 七、追加（2026-10-04 晚）：X01 压力档 50 分钟不结束 —— 现场复原

你转来的本机 AI 取证报告，结论方向**是对的**（"ALNS 早就跑完了，卡在求解后的辅助工作"），
但有一处需要更正：**卡住的不止是对照矩阵**，主因在它之前——**建模型阶段对 95 万库位逐一问路**。
两处都是同一个病根：**每个库位对/库位-站台对都当场跑一次 Dijkstra**。

### 代码级证据（本仓库实际代码）

| 位置 | 事实 |
|---|---|
| `wh/routing.rs::node_pair`（旧版） | 每次调用都 `(String, String)` 建键 → 命中也要 2 次堆分配 + 长 id 比较；未命中时 `topology::dijkstra_until` **每次分配两个 `O(|V|)` 的 `Vec<f64>`**；缓存上限 20 万，超了直接 `clear()` → 工作集一大就**永久性全部未命中** |
| `wh/routing.rs::sources` | 上限 64 个源，超了 `clear()` —— 大仓设备位置远超 64，同样是抖动式失效 |
| `slotting/mod.rs::build_costs` 等 | 逐库位调 `seconds_to_station`：95 万库位 × 2 站台 ≈ **190 万次问路**；X01 图节点约 8.2 万，单次未命中 ≈ 毫秒级 → 累计**几十分钟**，且**发生在预算检查之前**（30 s 的搜索预算约束不到它） |
| `slotting/search.rs::comparison_json` | 当前布局 / 随机布局两个基线各自 `rebuild` + `recompute_relocation`，逐单元再算一遍迁移代价（100 万单元 × 2） |

这解释了你看到的三个现象：单核 100 %、内存 4–6 GB（每次未命中两个 `O(|V|)` 向量 + `pair_cache` 抖动）、
以及"ALNS 30 s 就该停却还在跑"（预算只管搜索，管不到建模型和对照片段）。

### 你的 lldb/寄存器取证与代码的对应关系（已在 origin/main 源码上逐行核对）

寄存器读数落在 `slotting::search::run + 73468`、`seed_random_assignment` 之后的循环里，
对应的就是下面这条链——**每一个库存单元走一遍**：

```
SlottingState::rebuild(assignment)                       // 103 万单元
  └─ SlottingState::place(lu, loc)
       └─ track_relocation(model, lu)
            └─ relocation_contribution(...)
                 └─ relocation_seconds(model, from, to)
                      ├─ relocation_cache.get(&(from, to))   // 随机布局 → 基本全不命中
                      └─ route_model.seconds_between_locations(&id_from, &id_to, &shuttle)
                           ├─ self.location(from_id).cloned()   // BTreeMap 查 190 万条 + **深拷贝**结构体
                           ├─ self.location(to_id).cloned()     // 同上
                           └─ 最多 4 × node_seconds(node_a, node_b)
                                └─ node_pair(...)  // 20 万条上限，满了 clear() → 命中率≈0
                                     └─ topology::dijkstra_until(...)  // **两次 O(|V|) 向量分配 + 整图最短路**
```

也就是说：你看到的"每小时 18 万件、单件约 20 ms"与"每次全图寻路"完全吻合；
而且随机布局意味着 `(from,to)` 对几乎两两不同，缓存**天然失效**——这不是调参能救的，
只能把"逐对全图寻路"改成"一次建表、之后查表"。

另外两点补充：

- **旧版不止"随机对照"这一段**：`currentLayout` 基线一样要 `rebuild` 一遍（同样 103 万次），
  而**建模型阶段**（`location_costs`：95 万库位 × 2 站台）走的是同一个病根，
  只是发生在搜索之前、你采样时已经过去了。
- **30 s 预算只管搜索循环**：建模型、初始解、对照、核验、序列化都在预算之外，
  所以"30 秒就该结束"在旧版上不成立；本分支把这几个阶段全部纳入了 `WH_TIME` 计时。

### 本分支的修法（都不改变结果）

1. **端头行备忘录**（`end_rows`，128 MiB 预算）：端头之间一次整图 Dijkstra 后变成行内浮点读取。
   端头数 = 巷道 × 层 × 2 ≈ 2160，全部建行也就 2160 次 Dijkstra，而不是 190 万次。
2. **下标入口**：`relocation_seconds_by_index` / `seconds_between_location_indices` 不再构造临时节点 id 字符串；
   与字符串入口**逐位同值**（求和顺序、端头枚举顺序一致）。旧版每次调用还会 `location(id).cloned()`
   深拷贝两个结构体，现在也一并省掉。
3. **精确解探针提前判规模**：旧版在大实例上会先 `build_model` 一次、再发现"单元数超过
   `exactMaxUnits`，不做精确解"而白扔掉——白建一整个模型。现在先比规模再建。
   （诚实说明：40 次迭代的对照里这项的墙钟差异落在噪声内（86.97 s vs 90.18 s，机器同时在跑另一路对照），
   它是**结构性**的正确做法，收益随实例增大而增长。）
4. **可观测**：`WH_TIME=1` 现在会打印 `comparison:*` 分段耗时，以及迁移代价重算的
   **每 10 万单元进度**（stderr，不影响 stdout 的 JSON）——下次再遇到"卡住"不用反汇编。
