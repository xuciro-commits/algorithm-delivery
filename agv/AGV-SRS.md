# AGV Dispatch — 多车任务分配与调度引擎：数学模型与契约设计（M2）

| 项 | 内容 |
|---|---|
| 文档版本 | 1.0（随 M3 实现冻结） |
| 对应需求 | 总 SRS §6–§10（算法）、§11–§12（实验室）、§13（契约）、§18–§20（验收/验证/性能） |
| 定位 | 独立算法引擎：任务分配 + 顺序优化 + 时间安排，经**版本化契约**调用 MAPF 引擎完成时空路径 |

## 1. 问题定位（不是 MAPF 的另一个名字）

**输入**：共享栅格地图 + 车辆（初始位置/能力）+ 运输任务（取货点/送达点/释放时间/优先级/服务时长/可选截止）+ 共享工作站（多泊位、容量）。
**输出**：每个任务由哪台车执行、按什么顺序、何时执行，以及**全局无碰撞的完整时空时间线**。

决策分三层：

1. **分配层**（谁）：任务 → 车辆（单载货：车辆同时最多承载 1 个任务；任务不可拆分、不可转移已开始的任务）。
2. **排序层**（什么顺序）：每车的任务序列（含取货→送达成对约束与释放时间）。
3. **实现层**（何时/怎么走）：把任务序列编译为逐段的**联合**多车路径规划请求，交 MAPF 引擎求解，拼接为完整时间线，并经独立调度验证器证明无冲突。

## 2. 数学模型

### 2.1 地图与时间

- 复用 `mapf-problem/1.0` 地图语义：二维栅格 `G=(V,E)`，`.` 可通行 / `#` 障碍，4 邻接 + 等待，离散同步时步，单位时间代价。
- 时域：`T_max`（声明或 auto 上界，受能力档位约束）。所有时刻为整数步。

### 2.2 车辆（Vehicle）

```
vehicle = { id, start ∈ V, capabilities: [string], status: available|paused }
```

- v1 每车同时最多承载 1 个任务（单载货）；速度恒为 1 格/步（与 MAPF 运动模型一致）。
- 能力：任务声明 `required_capability`，车辆 `capabilities` 必须包含之，否则不允许分配。
- `paused` 车辆不参与调度（位置作为占用格保留）；载重/电池/异质速度为未来扩展，契约预留字段但 v1 引擎声明 `UNSUPPORTED`。

### 2.3 任务（Task）与生命周期

```
task = { id, pickup: loc, dropoff: loc, release_step ≥ 0, priority ≥ 1,
         pickup_service ≥ 0, dropoff_service ≥ 0, due_step: int|null,
         required_capability: string|null }
loc = [x,y] | { station: id }
```

生命周期（解中逐任务给出状态与时刻）：

```
待释放(release_step 之前) → 待分配 → 已分配 → 前往取货 → 取货中
  → 前往送达 → 送达中 → 已完成
失败终态：unassigned（无人可执行）/ leg_infeasible（段规划证明不可行）/ budget（预算耗尽）
```

约束：取货先于送达；取货动作不得早于 `release_step`；`due_step` 为软约束（计入延迟指标，不阻断）。

### 2.4 共享工作站（Station）

```
station = { id, cells: [[x,y]...], capacity ≥ 1 }
capacity ≤ cells.len()（默认 = cells.len()）
```

- 工作站 = **泊位格集合**：每格同一时刻至多 1 台车（栅格物理约束，即 MAPF 顶点约束）。
- `capacity` 为**资源容量**：同一工作站上**并发服务数**（同时处于 servicing_pickup/servicing_dropoff 的车辆数）≤ capacity，即使泊位数更多。
- 纯 `[x,y]` 位置 = 隐式单泊位、容量 1 的工作站。
- 泊位分配是调度决策的一部分（解中逐访问给出实际泊位格）。

### 2.5 停车（Parking）

`parking: [[x,y]...]`（可选）：完成全部任务的车按确定性规则（最近空闲、id 序）转移到停车格并驻留；未声明时车辆驻留于最后位置（并在 notes 中提示可能阻塞泊位——由调度器的泊位占用估计规避）。

### 2.6 硬约束（验证器逐条检查，见 §7）

1. 任务分配唯一性（一任务一车）；
2. 单载货（车辆任务区间两两不重叠）；
3. 取货先于送达、不早于释放时间；
4. 能力匹配；
5. 泊位占用 ≤ 1/格/步；工作站并发服务 ≤ capacity；
6. 服务时长精确（`pickup_service`/`dropoff_service` 步原地驻留）；
7. 执行历史不可变（动态重调度时 `t < T_snapshot` 的整条时间线逐格保持）；
8. 完整时间线满足 MAPF 时空约束：位置连续（同格或相邻）、不入墙、无顶点冲突、无对向边交换、驻留格持续占用；
9. 状态语义准确：`FEASIBLE`（全部完成且验证通过）/ `PARTIAL`（部分完成，逐任务给出原因）/ `UNKNOWN` / `INFEASIBLE`（结构性证明）/ `INVALID_INPUT` / `UNSUPPORTED` / `CANCELLED` 严格区分。

### 2.7 优化目标（分层 + 加权，量纲说明）

**第一优先级（字典序）**：完成任务数最大化。
**第二优先级（加权和，所有项均以"离散时间步"为单位，量纲一致）**：

```
cost = w_m·makespan + w_f·Σ flow_time + w_e·Σ empty_travel + w_l·Σ lateness
默认 w = (1, 1, 1, 1)，问题内 objective.weights 可覆盖
```

- `flow_time = dropoff_done − release_step`（任务完成总时长）；
- `empty_travel` = 空驶步数（未载货的移动步）；`lateness = max(0, dropoff_done − due_step)`；
- 车辆利用率、等待步数、行驶距离等作为**报告指标**，不进入目标函数。
- 引擎为启发式：**永不宣称 OPTIMAL**（SRS §19 口径）；质量以与基线的对照呈现。

## 3. 算法

### 3.1 基线 `baseline`（确定性）

按 `(release_step, −priority, id)` 排序任务；依次将任务指给"使该任务估计完成时间最早"的**有能力**车辆（估计 = 车辆当前序列末端位置到取货点/送达点的曼哈顿距离 + 服务时长，含释放等待与工作站容量检查）；车辆序列 = 指派顺序。不搜索、纯贪心，作为质量下界对照与回归锚点。

### 3.2 正式算法 `insertion-ls`（贪心插入 + 确定性局部搜索）

1. **构造**：遗憾值贪心插入——每轮计算各（任务,车辆,位置）最小与次小插入代价差（遗憾值），选遗憾值最大的任务按最小代价插入（对释放时间与容量做可行性筛查）；
2. **改进**（时间预算内迭代，首改进接受，按固定序枚举邻域）：
   - `relocate`：把某任务移到另一车辆序列的任意位置；
   - `swap`：两车各取一任务互换；
   - `reorder`：同车两任务换序；
   - 代价以 §3.1 的**时间线模拟估计器**评估（曼哈顿 + 泊位/容量簿记，O(序列长)）；
3. **确定性**：xorshift RNG（seed 驱动）+ 全序 tie-break（车辆/任务 id 字典序）；同输入+同参数 ⇒ 同方案（语义指纹一致）；
4. **预算**：`time_limit_ms` 到即停止搜索，用当前最优实现化。

### 3.3 实现层（MAPF 集成，见 §4）与失败语义

- 估计最优的分配/序列 → 逐段联合 MAPF 求解 → 真实时间线。
- 某任务段规划失败：先尝试同车内换序/延后（一次性重试），仍失败则该任务标记失败原因并从序列剔除（其余任务继续）→ 若有完成的任务则 `PARTIAL`，否则按失败类型给 `UNKNOWN`/`INFEASIBLE`。
- 全局预算（dispatch + 所有 MAPF 段 + 验证）受 `time_limit_ms` 约束，超限立即收敛到当前已验证的部分方案。

## 4. MAPF 集成协议（关键架构点）

### 4.1 原则

- AGV **不复制** MAPF 内部结构；仅通过 `mapf_engine::engine::solve_json`（公共 JSON API，契约 `mapf-problem/1.0`）调用。
- 逐段**联合**规划（一次求解包含全部需移动的车辆），绝不是"每车每段单独求解后拼接"。
- 完整时间线由**调度验证器**独立证明无冲突（双层次验证：MAPF 逐段 verify + AGV 全时间线 verify，分别报告）。

### 4.2 分段联合规划（stage loop）

```
τ₀ = 0；每车 mission = [取货点ᵢ, 送达点ᵢ ...] + 终态停车
循环：
  ① 组装 MAPF 段问题：
     - 参与 = 有待达航点且未 paused 的车辆（start=τ 时刻位置，goal=当前航点）；
     - 驻留车辆（服务中/空闲/已完工）不参与，其所在格在段地图中置为障碍（时间窗=段全程，因其下一动作必在下一 stage 之后）；
     - 地图 = 基础地图 ∪ 动态障碍事件（按 at/until 生效）；
     - horizon = auto；solver 参数继承（planner/w/预算）。
  ② solve_json 求解 → 段内全部参与车的无冲突路径（含 stay-at-target 驻留）。
  ③ 拼接：timeline[v] ← 段路径（τ 偏移）；提前到 goal 的车在段内驻留（stay-at-target 语义保证泊位占用）。
  ④ τ ← min{ 到达时刻 + 服务时长 }（下一"服务完成"事件；同刻批量处理）；
     服务完成的车 goal ← 下一航点（终态 → 停车/退出为驻留障碍）。
  ⑤ 无剩余航点时结束。
```

正确性论证：
- 段内无冲突由 MAPF 求解器 + 其独立 verify 保证；
- 段间：τ 时刻位置来自上一段已执行前缀（互异）；新段从这些位置出发重规划，边界步唯一属于新段，不存在跨段边交换；
- 服务时长 = 到达后原地驻留（stay-at-target 强制占用泊位格 → 其他车无法进入该格，容量=1 的物理占用自动成立）；
- 多泊位/容量资源在调度层簿记 + 验证器复核；
- **全时间线冲突由 AGV 验证器独立重演证明**（不信任拼接逻辑自身）。

### 4.3 服务时间映射

`pickup_service = S` ⇒ 车辆在取货泊位原地驻留 S 步（时间线 [到达, 到达+S] 位置不变），下一 stage 起点为该格。S=0 表示即时交接。

### 4.4 与 MAPF 语义的差异处理

| 差异 | 处理 |
|---|---|
| MAPF 机器人=单起终点；AGV 车=多航点序列 | 分段联合规划 + 段间 goal 推进（§4.2） |
| MAPF stay-at-target 占用终点 | 恰好建模"服务中/驻留占用泊位"；完工车转移停车格后以驻留障碍退出 |
| MAPF 无工作站容量概念 | 调度层泊位/容量簿记 + AGV 验证器独立检查（§7） |
| MAPF 起点不能等于终点 | 空闲/完工车不进 MAPF 段（作为驻留障碍），规避退化输入 |
| MAPF 超时/失败 | 段重试（同车换序一次）→ 任务级失败语义（§3.3），不伪造成功 |

### 4.5 动态重调度（事件驱动）

输入：`dynamic = { snapshot: { time: T, vehicles: {id: {pos, phase, task, path}}, tasks: {id: {status, assignee}} }, events: [...] }`（snapshot 由实验室/CLI 从当前解构造，引擎亦可从 `prior_solution` 派生）。

- 事件类型：`task_add / task_cancel(未开始) / task_priority / vehicle_pause / vehicle_resume / obstacle_add / obstacle_remove`；
- 不变量：`t < T` 的执行历史逐格保留；`已取货未送达` 的任务固定于原车（不可转移载货）；已完成任务保留；
- 从 T 起重跑 §3.1/3.2（仅剩余可调度任务）+ §4.2（初始位置 = snapshot 位置）；
- 输出：新旧时间线 diff 统计（受影响车辆、重调度耗时、路径变动步数、任务变动）。

## 5. 数据契约（Schema 见 `contracts/`，版本均为 `/1.0`）

| 契约 | 用途 |
|---|---|
| `AgvDispatchProblem` | 地图 + 车辆 + 任务 + 工作站 + 停车 + 目标权重 + 求解参数 + 动态块 |
| `AgvDispatchSolution` | 状态 + 逐车完整时间线/任务相位 + 逐任务分配与时刻 + 指标 + 搜索统计 + 验证内嵌 + 指纹 |
| `AgvDispatchVerification` | checks + violations（定位到车辆/任务/时刻/格）+ 指标复算 |
| `AgvDispatchCapabilities` | 档位限额（车辆 64 / 任务 128 / 格 16384 / 时域 4000 / 预算 120 s）+ 算法清单 + 扩展声明 |
| `AgvDispatchEvent` / `AgvDispatchSnapshot` | 动态块子结构（问题内嵌） |

两个引擎之间仅出现 `mapf-problem/1.0` 形状的段请求与 `mapf-solution/1.0` 形状的段结果（AGV 不感知 MAPF 内部类型）。

## 6. 固定验收数据（A01–A16，见 `mock/`）

小型人工可核对案例（含最优性参考/合法见证）+ 动态/负例/篡改样例，逐条对应总 SRS §18。验收由 `agv acceptance` 一键执行并产出机器可读报告。

## 7. 独立调度验证器（`verify.rs`，不信任求解器）

重演全部约束：§2.6 的 1–9 逐条 + 指标复算（completed/flow/makespan/空驶/等待/延迟/利用率）+ 动态模式历史保持。violations 携带 `code/where(vehicles,tasks)/at_step/cell/message`。**MAPF 验证通过 ≠ AGV 验证通过：两层分别报告。**

## 8. 基准测试计划（`bench/`）

| 档 | 规模 | 内容 |
|---|---|---|
| S | 3–5 车 / 5–10 任务 | 仓库小图，对照最优性参考（人工见证） |
| M | 10–20 车 / 20–50 任务 | room/maze 32×32 |
| L | 30–50 车 / 50–100 任务 | warehouse 161×63 |
| D | 动态 | 持续插入任务 + 车辆暂停/恢复 + 障碍事件 |

固定种子生成（确定性可复现）；每档 `baseline` vs `insertion-ls` 对照；报告完成数/目标值/耗时/失败与超时。硬门槛：**验证失败数必须为 0**（凡输出的方案必须两层验证通过）。

## 9. 交付边界（v1 不做）

连续运动/车辆动力学、电池、多车协同搬运、异质速度、WMS/WES/WCS 真实设备对接、任务拆分与转移载货、`OPTIMAL` 证明、跨仓库网络。以上在 capabilities 中以 `unsupported_features` 声明，请求即 `UNSUPPORTED`，不静默近似。
